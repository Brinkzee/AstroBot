## 阶段 0: Brainstorm 定稿

- **用户关键原话**:
  > "我要用 Superpowers 模式把客服系统里占位的分流器做成正式版,这是 Workflow 里最关键的节点。"
  > "1. 指代消解:用 LLM 结合对话历史,把「它能退吗」这种带指代的话补全成一句不依赖上下文也能看懂的完整问题;问题本身已完整、指代已明确的,原样透传,不强行改写"
  > "2. Query 改写:口语模糊问法归一成标准问法,和指代消解一并处理"
  > "3. Query 扩写:把一句问题泛化成多条侧重点不同的检索查询(强制 JSON 输出,字段就 queries 一个数组),几条一起检索再去重合并;只对退款退货、售后这类高频、容错低的核心场景做,简单 FAQ 不扩;扩写放检索侧现查现用,库里知识只留一份,不在入库侧拆存多份"
  > "4. 意图识别用 LLM prompt 路线,不训分类模型,prompt 按四件套写: 把七类意图(物流、订单、商品咨询、退款退货、售后、投诉、闲聊)枚举成选择题让模型选; 强制 JSON 输出,字段就 intent 和 confidence 两个; 给几个边界 few-shot 样例; 留「其他」兜底类,拿不准就归它,别硬塞进业务意图"
  > "5. 分流精化:退款退货和售后走一条确定性子流程——先拿订单数据、再做 Query 扩写并强制检索政策条款,最后只把「这一单能不能退」交给主力 Agent 判断"
  > "6. 槽位处理:缺订单号不让模型猜,执行阶段弹订单选择器让用户点选回填;退款原因不追问,用户提交退款单时从固定类目里自选;需求澄清留在主力 Agent 里做,意图识别只判「要干什么」"
  > "7. 前端配套:订单选择器做成聊天流里可点选的订单卡片,点选后自动回填、流程接着走;退款单是一个简单表单,退款原因从固定类目里下拉选"
  > 订单槽位中断回填机制确认：“方案A”（状态流事件驱动 + 自动发送）
  > 退款表单触发时机与类目确认：“确认”（Agent 判定满足退款时下发 apply_refund 动作，弹窗提供固定类目，提交至 /api/tickets）
  > 架构方案选择：“方案 1”（顶层图显式拆分子流程节点：订单提取/缺单拦截 -> Query 扩写与政策检索 -> 主力 Agent 裁决）
  > 模块 1~4 详细设计呈现阶段：“确认”

- **关键产出**:
  - Spec 设计规范路径: `docs/superpowers/specs/2026-09-11-router-refinement-design.md`
  - 核心架构决议:
    1. **显式子流程图拓扑（方案 1）**：LangGraph 主拓扑中引入 `refund_order_check`、`emit_order_selector`、`refund_expansion_retrieval`，形成严格确定性的退款处理水线；
    2. **指代消解与口语改写合一**：结合会话上下文精准补全「它能退吗」为完整自包含问题；严格实施「原样透传保护」，完整无歧义句子与寒暄不强行改写；
    3. **意图识别 Prompt 四件套**：8 分类枚举选择题（7 业务 + 1 「其他」兜底）、强 JSON（含 `confidence`）、边界 few-shot、大模型保底加小模型置信度级联降级策略；
    4. **核心场景检索侧 Query 扩写**：仅对退款退货/售后触发，LLM 输出 `{"queries": [...]}`，并发检索、内容哈希去重与分数重排，知识库物理单份存储；
    5. **订单槽位中断回填闭环（方案 A）**：缺单号时工作流在 `refund_order_check` 拦截，下发 `order_selector` 事件及 Mock 订单卡片，前端点选后自动发送 `退款订单: {order_id}` 续接；
    6. **主力 Agent 职责专一化**：预装真实订单数据与政策证据，Agent 仅专注裁决「这一单能不能退」，杜绝多余工具调用与退款原因追问；满足退款条件触发 `apply_refund`，前端弹窗自选固定类目提交工单。

- **用户拒绝或纠偏**:
  - 确认采用方案 A（状态流驱动 + 自动发送），避免 LangGraph 内部 interrupt/resume 对既有流式输出与消息持久化机制造成侵入；
  - 明确退款表单无需用户手打长文本，复用 `/api/tickets` 接口并限定固定类目下拉选。

- **翻车与返工**:
  - 无。

  > "4. 意图识别用 LLM prompt 路线,不训分类模型,prompt 按四件套写: 把七类意图(物流、订单、商品咨询、退款退货、售后、投诉、闲聊)枚举成选择题让模型选; 强制 JSON 输出,字段就 intent 和 confidence 两个; 给几个边界 few-shot 样例; 留「其他」兜底类,拿不准就归它,别硬塞进业务意图"
  > "技术栈: 意图识别默认配够格的大模型先把准确率做上去,成本吃紧时再走降级路:小模型给判断和置信度,置信度低才升级大模型重判一次"

- **关键产出**:
  - 代码实现: `app/services/workflow/nodes/pre_nodes.py`
  - 单元测试: `tests/test_workflow_intent_four_elements.py`（11 项测试全部 PASS，全量 270 项回归测试 100% 通过）
  - Git Commit: `5e8647752a24404d5bb901416bc39026fd3740f9` (`feat(workflow): implement intent recognition prompt four elements with confidence cascade`)
  - 独立代码审查: Spec Compliance: Spec ✅, Code Quality: Approved
  - 核心成果:
    1. 构建 `INTENT_FOUR_ELEMENTS_PROMPT`，集齐 8 分类枚举选择题（7 业务 + 1 兜底）、强制 JSON 输出（含 `confidence` 浮点数）、6 大边界 few-shot 样例（售后 vs 退款、催发货 vs 催退款、投诉、怪问题）与「其他」兜底保护规则；
    2. 实现生产级双层模型置信度级联降级策略：小模型高置信度（`>=0.85`）且为有效业务意图时直接采纳直通返回；低置信度（`<0.85`）或初判为「其他」或解析异常时，自动唤醒主力大模型重判与兜底把关；
    3. 新增 `other_fallback_node` 友好引导出口，对超出商城业务范围的离群提问直接给出专业亲和说明并推荐转人工客服 `["transfer_agent"]`；
    4. 具备高度健壮的容错机制：JSON 解析异常或模型故障时自动降级至 `intent="其他"`, `confidence=0.0`，向后兼容历史测试数据。
