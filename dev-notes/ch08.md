# 开发过程手记 (Dev Notes) - 第八章：客服系统即插即用工具体系与 MCP 协议集成

本文档用于追踪并留痕第八章（统一工具注册中心、JSON Schema 校验、读写权限门禁、统一超时重试与错误分诊执行引擎、无外键高可用工具调用审计、双独立业务 MCP Server 接入、以及基于 LangGraph Interrupt 的工单人机确认流）整个开发周期的关键决策、阶段产出、沟通纠偏与技术踩坑记录。

## 阶段 0: Brainstorm 定稿

- **用户关键原话**:
  > "sql/ch08-ddl.sql这是需要建的表 我要用 Superpowers 模式把客服系统的工具层从几个写死的内置工具,升级成即插即用的工具系统。"
  > "1. 工具注册中心:不管内置还是 MCP 来的工具,一律带齐工具名、用途描述、JSON Schema 参数定义三样,登记进同一份工具表;内置工具服务启动时登记,MCP 工具连上 Server 动态发现、现问现拿;新工具注册进来就能被主力 Agent 用上,不改核心代码、不重启服务"
  > "2. 参数校验:工具执行前统一按 JSON Schema 校验一遍,类型不对、必填缺失、取值越界的拦下;拦下不抛异常了事,把校验错误说明包成一条工具结果回灌给模型,让它追问用户或重新组织调用"
  > "3. 权限控制:工具分只读、写两类,写操作由执行引擎把门;本系统的写操作就 create_ticket 一个,规矩是——只有客户明确要求建工单时才发起,真正执行还要等第 7 点的前端确认回来,没确认的调用引擎直接拒绝,不给模型绕过去的机会;外部 MCP 工具的用途声明是对方自己写的、不可信,能不能调(尤其写操作)只认我们这侧的权限规则,不看 Server 声明、不让模型临场判断"
  > "4. 执行引擎:所有工具调用走同一处,统一管超时、重试、错误处理、结果格式化;重试只给网络抖动这类暂时性故障,业务空结果不重试,写操作默认不自动重试(超时未必没执行,重复执行比失败更糟);错误按参数不合法、查询落空、真故障三类分诊,坏消息如实回给模型;结果只挑回答用得上的字段、内部枚举码翻成人话、序列化 JSON 中文不转义"
  > "5. 审计留痕:建 tool_audit_logs 表,每次工具调用落一条——所属会话、tool_call_id、工具名、来源是内置还是哪个 MCP Server、调用参数、结果摘要、状态(成功/失败/超时/校验拦下/权限拒绝)、错误说明、重试次数、耗时、时间;被权限拒、被校验拦的调用同样要落;审计表不挂外键,写审计失败不许反过来拦工具执行"
  > "6. MCP 接入:自建两个业务 MCP Server——物流(查物流轨迹)、售后(查在保、查退货进度),各自独立进程,Server 内部照第 2 章工具的做法随机生成 mock 数据返回,不接真实系统、不建表;客服系统作为 MCP Client 接入,拿回的工具跟内置清单合成一份,主力 Agent 一视同仁地调;物流查询由物流 MCP Server 接管,第 2 章内置的 query_logistics 从清单里下线,别留重名工具"
  > "7. 建工单确认流(带前端配套):客户明确要求建工单才走这条流,Agent 先核对信息够不够,缺问题描述这类必填项就主动追问用户,不许瞎编;凑齐后发起 create_ticket,执行引擎不直接执行,照第 6 章订单选择器的做法用 LangGraph interrupt 把工单预览(工单类型、问题描述)推给前端;前端渲染成预览卡片,带「确认提交」「取消」两个按钮:点确认,回传后端 resume 放行,落 tickets 表,回复里把工单号带给用户;点取消,不执行,这次调用按「权限拒绝」落审计;第 5 章投诉流程里前端按钮建单那条路保持不动,点按钮本身就是用户确认"
  > 澄清问题 1（工单确认流 Resume 接口）：“选项A”（专设 Resume 流式接口 POST /api/chat/resume）
  > 澄清问题 2（执行引擎门禁与外部 MCP 权限判定）：“选项A”（双重门禁 + MCP 默认只读白名单制）
  > 架构方案确认：“采用方案1”（动态统一注册中心 + 契约化执行网关 + 原生 Interrupt 交互）
  > 详细设计第 1~4 部分分节呈现：“确认”

  > “增加一项用户的意图识别分类'人工：明确要求转人工、建工单或者找客服专员跟进的（无论是否有具体问题，只要提到[转人工/建工单]诉求就归为此类意图）'，'人工'意图识别出口归为'business_data'”

- **关键产出**:
  - Spec 设计规范路径: `docs/superpowers/specs/2026-09-14-plug-and-play-tools-design.md`
  - 核心架构决议:
    1. **统一工具注册中心与 MCP 接入**：重构 `ToolRegistry`，集成 `MultiServerMCPClient`，配置物流（8001端口）与售后（8002端口）两个独立 MCP Server（Streamable HTTP）；实现“现问现拿”动态工具发现，支持 MCP Server 增删工具零重启生效；内置 `query_logistics` 从注册表下线由 MCP 物流接管；
    2. **严格参数校验器与统一执行引擎**：提取 `args_schema` 进行必填项、类型及边界校验，失败落「校验拦下」回灌模型；统一 `ToolExecutor` 调度 5.0 秒超时、仅针对网络瞬时抖动重试 1 次（写操作与业务空结果恒不自动重试），将错误分诊为参数不合法、查询落空、真故障，格式化中文输出且 `ensure_ascii=False`；
    3. **零信任权限门禁与无外键审计**：外部 MCP 工具默认一律只读；`create_ticket` 仅在用户明确提出诉求且通过前端确认放行时执行；创建 `tool_audit_logs` 表 ORM 映射，无物理外键，独立异步 Session 落盘且异常静默降级；
    4. **LangGraph Interrupt 工单人机确认流**：信息不全主动追问绝不瞎编；发起 `create_ticket` 时调用 `interrupt` 挂起，下发 `ticket_preview` SSE 事件；前端渲染预览卡片；通过 `POST /api/chat/resume` 接收确认/取消并恢复执行（确认落库 tickets、取消记权限拒绝）；保留第 5 章投诉按钮直建工单逻辑；
    5. **意图识别 9 分类扩展与路由直通**：扩展 `VALID_INTENTS` 纳入“人工”意图（包含转人工、建工单或找专员等诉求），路由出口统一映射为 `"business_data"` 直通 `main_agent_node`，确保建单全流程闭环推进。

- **用户拒绝或纠偏**:
  - 用户提出补充需求：增加意图识别 9 分类中的「人工」分类（无论是否有具体问题，只要提到[转人工/建工单]即归为此类），并将路由出口强制映射为 `"business_data"` 直通主力 Agent，已在 Spec 3.7 节完成补充修订。

- **翻车与返工**:
  - 无。
