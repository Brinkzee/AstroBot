本文档用于追踪并留痕第九章（Langfuse 链路观测、意图维度 Token 成本归因、多信号校准置信度闸门、低置信度证据快照三路落池、FAQ 标准化与查重飞轮流水线、知识库双写回流、自动化评估流水线及观测与成本后台看板）整个开发周期的关键决策、阶段产出、沟通纠偏与技术踩坑记录。

## 阶段 0: Brainstorm 定稿

- **用户关键原话**:
  > "我要用 Superpowers 模式给客服系统装上眼睛,再把答不上的问题变成改进燃料。"
  > "1. 接 Langfuse:设环境变量、在 LangGraph 编译时挂一次回调;每条请求的完整 trace 树(每个节点的 prompt、工具调用、检索结果、token 消耗和耗时)都能在界面上铺开看"
  > "2. Cost Control:把意图识别结果打进 trace 元数据,按意图维度统计 token 花销,知道钱花在哪类问题上"
  > "3. 数据飞轮闭环,三个入口都把问题送进 ch04 建的 low_confidence_questions 问题池,各自标好入池入口;落池时把当轮的召回片段快照(Top 几条的原文和得分)一并存下,问题池新加一列,给人工审核当依据;👎 这种事后落池的,从该会话当轮的检索结果里尽力回捞,那一轮真没走检索(闲聊、业务数据类)才空着..."
  > "4. 飞轮流水线:问题标准化、查重、入待审队列(建 review_queue 表)...人工在后台审核,通过的走 ch03 落库流程写入知识库"
  > "5. 自动化评估流水线:复用 ch04 那份评估集和指标(检索段 Recall@K、MRR,生成段 Faithfulness)定期跑,每轮分数落 eval_runs 表...按时间连成趋势"
  > "6. 前端配套:待审队列做成一个简单的后台管理页...每行能点开详情,看到归并进来的用户原话和当时的召回片段..."
  > 澄清问题 1（Langfuse 降级策略）：“宽容降级”
  > 澄清问题 2（Cost Control 交付形式）：“方案A”（后端提供统计 API + CLI 验证命令）
  > 澄清问题 3（飞轮流水线触发时机）：“方案B”（纯手动/定时批处理，入池仅落表，待审队列通过后台一键触发或定时脚本批处理）
  > 架构方案确认：“方案1”（模块解耦分层架构）
  > 补充需求原话：“后台添加观测与成本页(三张终端报表搬进后台)...只读 API app/api/observability.py(GET /api/observability/overview)...不许出现第二个真相...三块互不连坐...重跑按钮走 ch03 那套作业运行器...推荐阈值与在用阈值不一致时页面明说...与其他后台页同一套外壳:导航加一格「观测与成本」,/admin 首页多一张卡。”

- **关键产出**:
  - Spec 设计规范路径: `docs/superpowers/specs/2026-09-15-observability-and-data-flywheel-design.md`
  - 核心架构决议:
    1. **Langfuse 编译期单点注入与宽容降级**：封装 `LangfuseService`，在 `build_workflow_graph` 编译期调用 `.with_config({"callbacks": [langfuse_handler]})` 挂载回调；未配 Key 时优雅降级为安全旁路；意图识别节点运行后动态向 Trace 根打入 `intent` 元数据与 tags；
    2. **意图成本控制 (Cost Control)**：提供 `scripts/check_intent_costs.py`，产出权威报表 `reports/cost_by_intent.json`，统计各意图总请求数、Prompt Token、Completion Token、总 Token、估算费用及占比，按消耗降序排序；
    3. **校准置信度闸门与多入口快照落池**：升级置信度为多信号算子（精排 Top1 得分、有效证据数、Top1-Top2 分差），由 `scripts/calibrate_confidence_gate.py` 基于 Ch04 评估集网格搜索最佳截断阈值产出 `reports/confidence_calibration.json`；三路入口（低置信度拦截、自评不足、用户 👎）统一持久化 `low_confidence_questions` 并记录召回片段快照 `retrieved_chunks`；
    4. **两阶段查重飞轮与双写回流**：批处理脚本/服务处理未归并原话，LLM FAQ 标准化改写并配示例答案，向量初筛+LLM 语义精判去重，命中累加计数，未命中新建 `review_queue` 记录；审核通过后调用既有 `KnowledgeDualWriter` 双写落库（MySQL + Milvus），完成闭环；
    5. **自动化评估与趋势落表**：`scripts/run_eval_pipeline.py` 复用 Ch04 评估集计算 Recall@3/5/10、MRR 和 Faithfulness，持久化至 `eval_runs` 表，对比上一轮计算 Delta 下滑预警；
    6. **后台观测与成本看板 (`/observability`)**：实现只读接口 `GET /api/observability/overview`，聚合意图成本账、评估趋势、阈值校准三块，三块互不连坐，不重算指标，重跑全部接入白名单作业调度器 `JobRunner`，检测阈值不一致时向用户报警提示回填配置。

- **用户拒绝或纠偏**:
  - 飞轮触发时机选择方案 B（手动/批处理运行，入池只做原子落表，待审队列批处理生成）；
  - 补充需求：将原来仅在终端的三张报表（意图成本账、评估趋势、置信度阈值校准）整体搬进后台统一观测页 `/observability`，要求只读 API、不出现第二个真相、三块互不连坐、重跑走白名单 `JobRunner`、阈值不一致提醒回填配置。

- **翻车与返工**:
  - 无。

  - 单元测试: `tests/test_ch09_pool_ingestion.py` (4 项测试 100% PASS，2.20 秒内秒级完成)
  - Git Commit:
    - `800c189` (`feat(flywheel): implement snapshot capture across 3 low-confidence entry points and feedback API`)
    - `2aef3d2` (`fix(tests): use AsyncClient instead of TestClient in test_ch09_pool_ingestion to avoid asyncio deadlock`)

- **用户拒绝或纠偏**:
  - 用户反馈测试挂起，触发 systematic-debugging 技能定位并根治。

- **翻车与返工**:
  - **根本原因**: `test_ch09_pool_ingestion.py` 中误用了同步 `TestClient` 测试异步 FastAPI 接口，且 `memory_db` 为运行于主线程事件循环上的 `aiosqlite` 异步会话。同步 `TestClient` 阻塞主线程等待，导致跨线程 BlockingPortal 与异步事件循环相互等待发生死锁。
  - **根治方案**: 全面将测试客户端重构为 `httpx.AsyncClient` 配合 `ASGITransport`，消除阻塞等待，测试耗时从无限死锁挂起缩减至 2.2 秒内全部通过。
